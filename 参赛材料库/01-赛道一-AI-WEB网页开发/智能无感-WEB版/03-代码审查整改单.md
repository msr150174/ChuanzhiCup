## P0-1：`infra-check.bat` 永远不执行 V2 建表脚本

### 位置
`转换-Java后端/guardian-server/infra-check.bat`

- **第 22–24 行**：只加载 V1
- **第 81–86 行**：表数量 ≥12 就 `goto :redis_step`，直接跳过建表

### 现状代码

```bat
REM L21-24
REM V1__init_schema.sql is now the znwg edition (creates database znwg)
set "SCHEMA=%SCRIPT_DIR%..\..\db\V1__init_schema.sql"
if not exist "%SCHEMA%" set "SCHEMA=%SCRIPT_DIR%db\V1__init_schema.sql"
if not exist "%SCHEMA%" set "SCHEMA=%SCRIPT_DIR%db\V1__init_schema_znwg.sql"

REM L79-86
REM ---------- check if database already has all tables ----------

if defined TBLCOUNT (
    if !TBLCOUNT! GEQ 12 (
        echo       already initialized ^(!TBLCOUNT! tables^)
        goto :redis_step
    )
)
```

### 问题分析

两个致命点叠加：

1. **`SCHEMA` 变量只指向 V1**，V2 从未被加载
2. **即便能把 V2 塞进 `SCHEMA`，第 82 行的 `GEQ 12` 判断也会让它跳过**——因为 V1 建完就是 12 张表，第 83 行直接 `goto :redis_step`

**结果**：`ai_call_logs` 表在任何情况下都不会被创建。

### 后果

评审老师按 README 启动 → 没有 `ai_call_logs` 表 → 管理员点「AI 研判」→ 写审计日志时报 SQL 异常 → **AI 分诊功能完全不可用**。

而这个功能正是赛道一 AI 技术深度 35% 的核心载体。

### 整改要求

在 V1 建表逻辑之后、`:redis_step` 之前，**增加独立的 V2 迁移检查**（不要塞进 V1 的流程里）。

**建议实现**：

```bat
REM ========== V2 migration: ai_call_logs ==========
set "SCHEMA_V2=%SCRIPT_DIR%..\..\db\V2__ai_triage.sql"
if not exist "%SCHEMA_V2%" set "SCHEMA_V2=%SCRIPT_DIR%db\V2__ai_triage.sql"

if exist "%SCHEMA_V2%" (
    REM 单独检查 ai_call_logs 是否存在
    "%MYSQL_BIN%" -u%DB_USER% -p%DB_PASS% -N -B ^
      -e "SELECT COUNT(*) FROM information_schema.TABLES WHERE TABLE_SCHEMA='%DB_NAME%' AND TABLE_NAME='ai_call_logs'" ^
      > "%TEMP%\guardian_v2_check.txt" 2>nul

    set /p V2_EXISTS=<"%TEMP%\guardian_v2_check.txt"
    if "!V2_EXISTS!"=="0" (
        echo       applying V2 ^(ai_call_logs^)...
        copy /y "%SCHEMA_V2%" "%TEMP%\guardian_schema_v2.sql" >nul
        set "V2_FWD=%TEMP%\guardian_schema_v2.sql"
        set "V2_FWD=!V2_FWD:\=/!"
        "%MYSQL_BIN%" -u%DB_USER% -p%DB_PASS% --default-character-set=utf8mb4 ^
          -e "source !V2_FWD!" >nul 2>&1
        echo       V2 applied
    ) else (
        echo       V2 already applied ^(ai_call_logs exists^)
    )
    del /q "%TEMP%\guardian_v2_check.txt" >nul 2>&1
)
```

### 验收标准

- [ ] 在**已有 12 张表**的老库上运行 `start.bat`，`ai_call_logs` 被创建
- [ ] 再次运行不会报错（幂等）
- [ ] 全新空库运行，V1 + V2 都建好，共 13 张表

> ⚠️ **注意**：`V2__ai_triage.sql` 第 8 行有 `DROP TABLE IF EXISTS ai_call_logs;`
> **这在生产环境是危险的**——每次执行都会清空审计日志。

## P0-2：`AdminAiController` 类注解错误，SSE 方法缺 `@ResponseBody`

### 位置
`转换-Java后端/guardian-server/src/main/java/com/guardian/controller/AdminAiController.java`

| 行号 | 现状 | 问题 |
|---|---|---|
| **L33** | `@Controller` | ❌ 类级别是 `@Controller` 而非 `@RestController` |
| **L51** | `@GetMapping(value = "/alert/{alertId}/triage", produces = "text/event-stream")` | ❌ **没有 `@ResponseBody`** |
| **L52** | `public SseEmitter triageStream(...)` | ← 返回 SseEmitter |

- 编译期无任何错误（这就是为什么编译通过了）
- 运行期 500 或返回空白页
- **SSE 完全不通**

这类问题最容易被忽略——**能编译、能启动、一调用就废**。

### 整改要求

**方案 A（推荐，最简）**：类注解改为 `@RestController`

```java
@Slf4j
@RestController                    // ← 改这里，L33
@RequestMapping("/admin/ai")
@RequiredArgsConstructor
public class AdminAiController {
```

改完后 L94 的 `@ResponseBody` 可以删掉（`@RestController` 已隐含）。

**方案 B（不推荐）**：保持 `@Controller`，在 L51 后面补 `@ResponseBody`

```java
@GetMapping(value = "/alert/{alertId}/triage", produces = "text/event-stream")
@ResponseBody                      // ← 补这一行
public SseEmitter triageStream(HttpServletRequest req, @PathVariable String alertId) {
```

- [ ] 用 Postman/curl 请求 `GET /api/admin/ai/alert/{id}/triage`（带管理员 Token）

## P1-4：`triageStream` 中的线程与异常处理

### 位置
`AdminAiController.java` L63–L85

```java
new Thread(() -> {
    try {
        emitter.send(...);
        aiGuardianService.triage(alert, adminId, (type, content) -> {
            try {
                emitter.send(...);
            } catch (IOException e) {
                throw new RuntimeException(e);     // ← 包装成 RuntimeException
            }
        });
        ...
    } catch (Exception e) {
        ...
        emitter.completeWithError(e);
    }
}, "ai-triage").start();
```

### 问题

1. **`new Thread()` 裸创建**：无上限、无池化。若管理员快速点击多条告警，会创建大量线程
2. **`RuntimeException(e)` 丢失原始类型**：外层 catch 只能拿到 `RuntimeException`，日志里看不到是 IO 问题还是业务问题
3. **`completeWithError` 后再 `send("error")`**：顺序颠倒。L81 先 send 再 L83 completeWithError，但 send 可能已经失败

### 整改建议（不阻断，但建议改）

```java
// 1. 用线程池代替裸 new Thread
@Bean("aiTriageExecutor")
public Executor aiTriageExecutor() {
    ThreadPoolTaskExecutor ex = new ThreadPoolTaskExecutor();
    ex.setCorePoolSize(2);
    ex.setMaxPoolSize(4);
    ex.setQueueCapacity(20);
    ex.setThreadNamePrefix("ai-triage-");
    ex.initialize();
    return ex;
}

// 2. 保留原始异常类型
catch (IOException e) {
    throw new UncheckedIOException(e);
}

// 3. 调整顺序
try {
    emitter.send(event("error").data("分诊过程中断"));
} catch (IOException ignore) {}
emitter.complete();               // 正常结束，不带异常
```
