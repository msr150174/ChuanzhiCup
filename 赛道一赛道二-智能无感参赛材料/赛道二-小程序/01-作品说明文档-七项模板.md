# a. 项目说明

## a.1 项目背景

我国正快速进入深度老龄化社会，**独居老人**群体的日常安全与健康监护成为突出社会问题：

- 子女异地工作，无法 24 小时陪伴
- 独居老人突发状况（跌倒、突发疾病）难以及时发现
- 老年人对复杂 App 接受度低，需要**极简、大字号、少操作**的交互
- 传统智能硬件价格高、安装门槛高，难以普及

**本项目定位**：以微信小程序为轻量载体，用 AI 能力替代部分"看护"职责，为独居老人提供**低门槛、可持续、可负担**的健康守护。

## a.2 目标用户

| 用户角色 | 画像 | 核心诉求 |
|---|---|---|
| **主用户：独居/空巢老人** | 60 岁以上，手机使用能力有限 | 操作简单、大字号、一键求助 |
| **协作用户：子女/家属** | 30–50 岁，异地工作 | 远程查看长辈状态、接收告警 |
| **管理用户：服务机构** | 社区/养老机构工作人员 | 批量管理、告警处理 |

## a.3 使用场景

| 场景 | 描述 |
|---|---|
| **日常节律** | 老人每日作息打卡，系统计算睡眠评分并给出建议 |
| **紧急求助** | 老人长按 3 秒触发 SOS，自动通知家属并上报位置 |
| **异常告警** | 跌倒检测、心率异常、长时间无活动 → 自动告警 |
| **AI 陪伴** | 老人用语音/文字与 AI 助手"小护"对话，获取健康建议 |
| **用药提醒** | 定时提醒服药，记录服药情况 |
| **家属远程守护** | 子女查看健康报告、告警历史、位置 |

## a.4 核心功能清单

| # | 模块 | 功能 | 页面数 |
|---|---|---|---|
| 1 | **节律守护** | 作息打卡、睡眠评分、天气、周历、今日活动 | 4 |
| 2 | **居家守护** | SOS 求助（长按 3 秒）、设备状态、告警列表 | 4 |
| 3 | **健康监测** | 语音/图像/文本三模态分析、**跌倒检测**、监测历史 | 5 |

| 5 | **个人中心** | 用户资料、家庭成员、用药提醒、健康报告 | 8 |
| 6 | **登录注册** | 手机验证码登录、微信登录、找回密码 | 3 |

## b.2 微信云开发能力

本项目**未使用微信云开发**，采用自建后端架构（Spring Boot + MySQL 8 + Redis）。

**选择自建后端的原因**：

| 考虑 | 说明 |
|---|---|
| **函数时长限制** | 云函数有执行时长上限，本项目 AI 调用需长链路编排（Ollama 超时即降级至 Coze），云函数难以承载 |
| **依赖包大小** | 云开发对依赖包有体积限制，本项目需 Spring Boot 全套 + 腾讯云 OCR/SMS SDK |
| **数据库复杂度** | 12 张表 + 复杂统计聚合，需要 MySQL 的索引与事务能力 |
| **运维可控性** | 需要精细控制 Redis 缓存、连接池、日志，便于排查 AI 降级链路问题 |
| **接口规模** | 153 个接口，云函数的单函数模型不适合这种规模的业务系统 |

> 云开发的轻量优势在单页场景明显，但本项目属于**多模块、强 AI 编排**的垂直业务系统，自建后端更合适。
> 这是基于业务特点的**主动架构选择**，而非能力限制。

## b.3 AI 能力清单（**重点**）

### b.3.1 AI 架构：三层降级

```
① Ollama 本地模型（qwen2.5:7b）
   ├─ 优点：最快、最省钱、数据不出本地
   └─ 缺点：需本地部署
        ↓ 失败 / 超时
② Coze 云端智能体
   ├─ 优点：能力强、支持复杂推理
   └─ 缺点：需 Token、有额度成本
        ↓ 失败 / 超时
③ 本地规则库（12 条规则）
   └─ 优点：永远可用、零延迟
```

**设计价值**：任何一层失败自动降级，**用户永远不会看到报错**。这是老年用户产品的刚性要求。

### b.3.2 AI 能力矩阵

| AI 能力 | 接口 | 技术实现 | 业务价值 |
|---|---|---|---|
| **对话问答** | `POST /api/ai/chat` | LLM + 上下文 | 健康咨询、情绪陪伴 |
| **增强对话** | `POST /api/ai/chat/enhanced` | 规则前置 + LLM | 低延迟 + 高质量 |
| **文本分析** | `POST /api/monitor/text-analyze` | 意图识别 + 情绪分析 | 识别消极情绪，预警心理风险 |
| **语音分析** | `POST /api/monitor/voice-analyze` | ASR + 语义分析 | 语音陪伴、异常声音检测 |
| **图像分析** | `POST /api/monitor/image-analyze` | OCR + 多模态理解 | 药品识别、报告解读 |
| **视频帧分析** | `POST /api/monitor/analyze-frame` | 视觉模型 | 活动状态判断 |
| **跌倒检测** | `POST /api/monitor/fall-detect` | 姿态/运动特征 | **紧急安全兜底** |
| **睡眠分析** | `POST /api/ai/sleep-analysis` | 时序数据分析 | 睡眠质量评估 |
| **健康报告** | `GET /api/ai/report/daily`、`/weekly` | 数据聚合 + LLM 生成 | 周期性健康总结 |
| **语音合成** | `POST /api/ai/tts` | TTS | 语音播报，适老化 |

### b.3.3 规则库设计（第三层兜底）

12 条关键词规则，覆盖老年用户最常问的话题：

| # | 关键词 | 回复内容 |
|---|---|---|
| 1 | 你好/您好/嗨 | 自我介绍「小护」 |
| 2 | 健康/身体/体质 | 健康评分 |
| 3 | 步数/运动/走路 | 当日步数 |
| 4 | 睡眠/睡觉/失眠 | 睡眠时长 |
| 5 | 提醒/服药/吃药 | 引导设置提醒 |
| 6 | 心情/情绪/压力 | 情绪陪伴 |
| 7 | 吃/饮食/饭 | 饮食建议 |
| 8 | 位置/在哪 | 位置查询 |
| 9 | 紧急/求救/sos | SOS 引导 |
| 10 | 家人/家属/绑定 | 家人绑定引导 |
| 11 | 谢谢/感谢 | 礼貌回应 |
| 12 | 再见/晚安 | 告别 |

> **设计细节**：关键词刻意收窄。例如"健康/身体"规则**不含"怎么样"**这类泛词，
> 否则"我今天睡眠怎么样"会被这条抢先命中，走不到睡眠规则。
> 这是实测中发现并修正的问题。

### b.3.4 安全设计

| 设计 | 说明 |
|---|---|
| **密钥不下发前端** | 所有 AI 调用经后端中转，Token 存环境变量 |
| **降级不报错** | 三层兜底，用户永远拿到回复 |
| **不替代医疗诊断** | AI 回复明确"建议仅供参考，请遵医嘱" |
| **数据最小化** | 仅采集健康守护必需数据 |

# c. 创新点说明（**六维度，评分权重 20%**）

## c.1 AI 应用创新

**三模态健康感知 + 跌倒检测的主动守护**

传统健康 App 是"用户主动记录"，本项目实现"**AI 主动发现**"：

- 语音/图像/文本三模态分析，覆盖老年人表达不便的场景
- 跌倒检测作为"救命兜底"，在用户无法主动求助时自动响应
- 12 条规则库保证 AI 在任何网络条件下可用

## c.2 场景创新

**"老人—家属"双向守护闭环**

市场上多数适老化产品只服务一方：
- 只做老人端 → 家属无法感知
- 只做家属端 → 老人不会用

本项目通过**家庭成员绑定**把两端连起来：老人只需打卡 + SOS，家属端获取完整数据与告警。**降低老人学习成本，同时满足家属的知情需求。**

## c.3 产品创新

**适老化 + 专业化的双界面**

| 老人端 | 家属端 / 后台 |
|---|---|
| 大字号、大按钮 | 数据看板、告警处理 |
| 少层级、少输入 | 多维度统计 |
| 语音优先 | 批量管理 |

同一套后端，两套信息架构。**后台管理端（Vue）独立部署**，服务社区/机构场景。

## c.4 技术创新

**三层 AI 降级的鲁棒性架构**

```
Ollama（本地、免费、快）→ Coze（云端、强、有成本）→ 规则库（永远可用）
```

- 解决了"云端 AI 不可靠导致的用户体验崩塌"
- 解决了"老年用户无法理解技术错误"的问题
- 成本可控：优先走免费本地模型

**另一个技术点**：原项目有 5 处密钥泄露（含前端硬编码 Token），本次重构将全部 AI 调用后移到后端，**前端零密钥**。这既是安全改进，也是架构正确性证明。

## c.5 商业模式创新

【待填，取决于小程序主体类型】

**若为个人主体**（无法开通支付）：

- 免费基础版 + 增值服务（付费问诊导流、健康师咨询）
- 与社区/养老机构合作，机构付费、老人免费
- 硬件联动（智能手环/跌倒检测器）分成

**若为企业主体**：

- B2C 订阅：家属端高级功能（多长辈管理、健康报告导出）
- B2B 服务：社区/养老机构批量部署，按人头收费
- 硬件 + 服务套餐

## c.6 用户体验创新

**适老化设计的系统性落地**

| 设计点 | 做法 |
|---|---|
| **大字号模式** | 原项目有 CSS 但未挂载，本次修复并加开关 |
| **长按 SOS** | 3 秒长按（原代码实际 1 秒，与文案不符，已修正） |
| **语音优先** | 支持语音输入，减少打字 |
| **TTS 播报** | 回复可语音朗读 |
| **错误友好** | 任何 AI 失败都降级，不显示技术错误 |
| **真实数据** | 原项目睡眠评分是硬编码假数据，本次改为真实计算 |

> 💡 **"修复了 14 处原项目缺陷"这件事本身可以作为创新点讲**——它体现工程严谨性。
> 详见项目 `README.md` 第八节。

```java
/**
 * AI 编排服务 —— 三层降级
 * 路由顺序（任何一层失败都自动降级，绝不向用户报错）：
 *   ① Ollama（本地模型，最快最省钱）
 *   ② Coze（云端模型，能力强）
 *   ③ 规则库（本地兜底，永远可用）
 */
public String chat(String userId, String message) {
    if (aiEnabled) {
        String r = tryOllama(message);
        if (r != null) return r;
        r = tryCoze(message);
        if (r != null) return r;
    }
    return ruleProvider.reply(message, context);   // 兜底
}
```

本作品前身为 `ai-rhythm-guardian v3.0.0`（Taro + React 技术栈），经完整重构为当前版本（uni-app + Vue 3 + Spring Boot）。
**重构过程留存了完整的技术分析与决策记录**，可追溯、可验证。

| 项目名 | ai-rhythm-guardian | AI 节律守护 · 智能无感 |
| 前端 | Taro 4.1.9 + React 18 + Tailwind 4 + Zustand | **uni-app 3.0 + Vue 3 + TypeScript + Pinia** |
| 后端 | NestJS + Supabase（PostgreSQL） | **Spring Boot 3.2.5 + MyBatis + MySQL 8 + Redis** |

#### 二、相对原版本的优化部分

本次迭代修正原项目 **14 处缺陷**，并完成 **5 类关键升级**：

##### 2.1 安全问题修复（最重要）

| # | 原问题 | 修正 |
|---|---|---|
| 1 | **Coze Token 硬编码在前端**（`coze.config.ts`、`ai-chat/index.tsx`），编译进小程序包可被反编译提取 | 所有 AI 调用后移到后端，Token 存环境变量，**前端零密钥** |
| 2 | **高德 Key 硬编码在前端** | 同上，改为后端中转 |
| 3 | 密钥同时存在于 `server/.env` | 统一的 `.env` 管理 + `.gitignore` 排除 |
| 4 | `application.yml` 中密钥作为默认值 | 改为空默认值，强制环境变量注入 |
| 5 | 文档中记录了泄露密钥原文 | 全部脱敏处理 |

> 完整的《安全审计报告》随项目提交，记录了全部 5 类泄露点的位置、风险等级与处理方式。

##### 2.2 功能缺陷修复（14 处）

| # | 原问题 | 修正 |
|---|---|---|
| 1 | **跌倒检测 `handleEmergencySOS()` 写在 `if (detected)` 块外 → 每次都弹 SOS** | 移入条件块内，仅在真检测到跌倒时触发 |

| 12 | 设置项不持久化 | localStorage 持久化 |
| 13 | 5 处密钥泄露 | 改为后端中转 |

# g. 落地规划

> 以下内容已定稿（依据"前期个体 → 后续企业"主体路线），详见 `04-落地规划-g项定稿.md`


#### 一、主体与合规路线

本项目采取**"个人主体验证 → 企业主体商用"**的两阶段路线：

| 阶段 | 主体 | 时间 | 目标 | 商业能力 |
|---|---|---|---|---|
| **第一阶段** | 个人主体 | 参赛期间 – 2027 Q1 | 验证产品价值、积累真实用户、收集反馈 | 订阅消息、分享传播（**无支付**） |
| **第二阶段** | 企业主体 | 2027 Q2 起 | 商业化运营、接入硬件、拓展 B 端 | 支付、认证、类目扩展 |

**为什么先个人后企业**：

- 个人主体当月即可上线，**验证周期短、试错成本低**
- 企业主体需注册公司、资质审核、认证费用，前置投入大
- 先在真实用户中验证 AI 守护的价值，再决定商业投入规模

**主体升级时需完成**：小程序主体变更迁移、历史用户数据合规迁移、类目资质补齐。

#### 二、上线计划

| 阶段 | 时间 | 关键动作 | 里程碑 |
|---|---|---|---|
| **体验版** | 2026 年 11 月 | 完成体验版配置、小范围试用 | 10 户家庭试用 |
| **正式上线** | 2026 年 12 月 | 提交审核、公开发布（个人主体） | 通过审核 |

#### 三、用户增长设计

##### 3.1 核心洞察：**从"子女"切入，而非从"老人"切入**

老人不会主动搜索下载健康 App，但**子女会为父母的健康焦虑而主动寻找方案**。

```
子女发现问题（父母独居/跌倒担忧）
        ↓
搜索/朋友推荐 → 下载注册 → 生成邀请码
        ↓
老人扫码绑定（零学习成本进入）
        ↓
形成"子女-老人"双端留存
```

**这个路径的关键优势**：获取的是**有付费意愿的决策者**（子女），而非用户本身（老人）。

##### 3.2 传播路径

| 渠道 | 方式 | 优先级 |
|---|---|---|
| **微信分享** | 已接入分享能力，家属邀请家人共同关注 | P0 |
| **社区地推** | 与养老服务中心、社区居委会合作，现场协助安装 | P1 |
| **医院/药店** | 慢性病管理场景导流（需企业主体与资质） | P2 |
| **口碑裂变** | 用得好的家庭推荐给同龄朋友 | 自然增长 |

##### 3.3 增长目标

| 时间 | 目标用户 | 依据 |
|---|---|---|
| 上线首月 | 50 户 | 种子用户 |
| 6 个月 | 500 户 | 社区试点 + 口碑 |
| 12 个月 | 2,000 户 | 主体升级 + 多社区 |
| 24 个月 | 10,000 户 | 规模化 |

#### 四、运营机制

| 环节 | 设计 | 目的 |
|---|---|---|
| **激活** | 绑定家属后立即推送"首次守护报告" | 让用户 30 秒内看到价值 |
| **留存** | 每日打卡提醒 + 每周健康报告 | 形成习惯 |
| **防流失** | 连续 3 天未打卡 → 同时提醒老人与家属 | 双端唤醒 |
| **活跃** | 连续打卡天数、健康分提升、月度总结 | 游戏化激励 |
| **服务闭环** | 告警 → 家属处理 → 处理结果记录 | 保证告警不被忽略 |
| **反馈** | 内置反馈入口，每周汇总 | 持续迭代依据 |

**关键设计**：**防流失用双端提醒**。老人可能忽略提醒，但家属不会——家属的提醒才是真正的召回力量。

#### 五、商业闭环

##### 5.1 第一阶段（个人主体，无支付）

**模式：免费 + 价值验证**

```
成本端                          收入端
├─ 云服务器（轻量级）            └─ 暂无直接收入
├─ AI API（三层降级可控成本）        目标：积累用户与口碑
├─ 短信费用                         为第二阶段谈合作准备数据
└─ 运营人力
```

**成本控制的三个杠杆**（已实现）：

1. **优先走 Ollama 本地模型** —— 零 API 成本
2. **Coze 仅作第二层兜底** —— 用量在最坏情况下也可控
3. **规则库永远可用** —— 极端情况下零成本运行

> 💡 **这个成本结构是核心优势**：多数 AI 应用的成本模型不成立（用户越多亏越多），
> 而三层降级天然实现了"**低成本优先**"，是可持续的前提。

##### 5.2 第二阶段（企业主体，可支付）

**四条收入路径**：

| 路径 | 模式 | 客单价估算 | 优先级 |
|---|---|---|---|
| **B2C 订阅** | 家属端高级功能：多长辈管理、健康报告导出、AI 深度分析 | 9.9–29.9 元/月 | P0 |
| **B2B 机构服务** | 社区/养老机构批量部署，按人头或按机构收费 | 500–5000 元/月/机构 | P0 |
| **硬件联动** | 智能手环/跌倒检测器销售分成 | 按台分成 | P1 |
| **健康服务导流** | 在线问诊、康复指导等合作分成 | 按转化分成 | P2 |

**关于第一条路径的说明**：基础守护功能（打卡、SOS、告警、基础 AI 对话）**永久免费**，
付费的是"家属端的增强功能"——这符合老年人的付费习惯（老人不付费，子女愿付费）。

##### 5.3 单位经济模型（估算）

```
单家庭月度成本：
  AI 调用（走 Ollama 优先）      ≈ 0.5–2 元
  服务器分摊                     ≈ 0.3 元
  短信（告警触发时）              ≈ 0.1–0.5 元
  ─────────────────────────────────────
  合计                          ≈ 1–3 元/月

单家庭月度收入（订阅模式）：
  基础版                        0 元
  高级版                        9.9–29.9 元

毛利率：高级版 ≈ 70–90%
```

> 【待填】以上为估算，若有真实 API 用量数据请替换为实测值。
