# a. 项目说明

## a.1 项目背景

我国正快速进入深度老龄化社会，**独居老人**群体的日常安全与健康监护成为突出社会问题：

- 子女异地工作，无法 24 小时陪伴
- 独居老人突发状况（跌倒、突发疾病）难以及时发现
- 老年人对复杂 App 接受度低，需要**极简、大字号、少操作**的交互
- 传统智能硬件价格高、安装门槛高，难以普及

**本项目定位**：以微信小程序为轻量载体，用 AI 能力替代部分"看护"职责，为独居老人提供**低门槛、可持续、可负担**的健康守护。

## a.2 目标用户

| 用户角色 | 画像 | 核心诉求 |
|---|---|---|
| **主用户：独居/空巢老人** | 60 岁以上，手机使用能力有限 | 操作简单、大字号、一键求助 |
| **协作用户：子女/家属** | 30–50 岁，异地工作 | 远程查看长辈状态、接收告警 |
| **管理用户：服务机构** | 社区/养老机构工作人员 | 批量管理、告警处理 |

## a.3 使用场景

| 场景 | 描述 |
|---|---|
| **日常节律** | 老人每日作息打卡，系统计算睡眠评分并给出建议 |
| **紧急求助** | 老人长按 3 秒触发 SOS，自动通知家属并上报位置 |
| **异常告警** | 跌倒检测、心率异常、长时间无活动 → 自动告警 |
| **AI 陪伴** | 老人用语音/文字与 AI 助手"小护"对话，获取健康建议 |
| **用药提醒** | 定时提醒服药，记录服药情况 |
| **家属远程守护** | 子女查看健康报告、告警历史、位置 |

## b.3 AI 能力清单（**重点**）

### b.3.1 AI 架构：三层降级

```
① Ollama 本地模型（qwen2.5:7b）
   ├─ 优点：最快、最省钱、数据不出本地
   └─ 缺点：需本地部署
        ↓ 失败 / 超时
② Coze 云端智能体
   ├─ 优点：能力强、支持复杂推理
   └─ 缺点：需 Token、有额度成本
        ↓ 失败 / 超时
③ 本地规则库（12 条规则）
   └─ 优点：永远可用、零延迟
```

**设计价值**：任何一层失败自动降级，**用户永远不会看到报错**。这是老年用户产品的刚性要求。

### b.3.2 AI 能力矩阵

| AI 能力 | 接口 | 技术实现 | 业务价值 |
|---|---|---|---|
| **对话问答** | `POST /api/ai/chat` | LLM + 上下文 | 健康咨询、情绪陪伴 |
| **增强对话** | `POST /api/ai/chat/enhanced` | 规则前置 + LLM | 低延迟 + 高质量 |
| **文本分析** | `POST /api/monitor/text-analyze` | 意图识别 + 情绪分析 | 识别消极情绪，预警心理风险 |
| **语音分析** | `POST /api/monitor/voice-analyze` | ASR + 语义分析 | 语音陪伴、异常声音检测 |
| **图像分析** | `POST /api/monitor/image-analyze` | OCR + 多模态理解 | 药品识别、报告解读 |
| **视频帧分析** | `POST /api/monitor/analyze-frame` | 视觉模型 | 活动状态判断 |
| **跌倒检测** | `POST /api/monitor/fall-detect` | 姿态/运动特征 | **紧急安全兜底** |
| **睡眠分析** | `POST /api/ai/sleep-analysis` | 时序数据分析 | 睡眠质量评估 |
| **健康报告** | `GET /api/ai/report/daily`、`/weekly` | 数据聚合 + LLM 生成 | 周期性健康总结 |
| **语音合成** | `POST /api/ai/tts` | TTS | 语音播报，适老化 |

### b.3.3 规则库设计（第三层兜底）

12 条关键词规则，覆盖老年用户最常问的话题：

| # | 关键词 | 回复内容 |
|---|---|---|
| 1 | 你好/您好/嗨 | 自我介绍「小护」 |
| 2 | 健康/身体/体质 | 健康评分 |
| 3 | 步数/运动/走路 | 当日步数 |
| 4 | 睡眠/睡觉/失眠 | 睡眠时长 |
| 5 | 提醒/服药/吃药 | 引导设置提醒 |
| 6 | 心情/情绪/压力 | 情绪陪伴 |
| 7 | 吃/饮食/饭 | 饮食建议 |
| 8 | 位置/在哪 | 位置查询 |
| 9 | 紧急/求救/sos | SOS 引导 |
| 10 | 家人/家属/绑定 | 家人绑定引导 |
| 11 | 谢谢/感谢 | 礼貌回应 |
| 12 | 再见/晚安 | 告别 |

> **设计细节**：关键词刻意收窄。例如"健康/身体"规则**不含"怎么样"**这类泛词，
> 否则"我今天睡眠怎么样"会被这条抢先命中，走不到睡眠规则。
> 这是实测中发现并修正的问题。

### b.3.4 安全设计

| 设计 | 说明 |
|---|---|
| **密钥不下发前端** | 所有 AI 调用经后端中转，Token 存环境变量 |
| **降级不报错** | 三层兜底，用户永远拿到回复 |
| **不替代医疗诊断** | AI 回复明确"建议仅供参考，请遵医嘱" |
| **数据最小化** | 仅采集健康守护必需数据 |

# c. 创新点说明（**六维度，评分权重 20%**）

## c.1 AI 应用创新

**三模态健康感知 + 跌倒检测的主动守护**

传统健康 App 是"用户主动记录"，本项目实现"**AI 主动发现**"：

- 语音/图像/文本三模态分析，覆盖老年人表达不便的场景
- 跌倒检测作为"救命兜底"，在用户无法主动求助时自动响应
- 12 条规则库保证 AI 在任何网络条件下可用

## c.2 场景创新

**"老人—家属"双向守护闭环**

市场上多数适老化产品只服务一方：
- 只做老人端 → 家属无法感知
- 只做家属端 → 老人不会用

本项目通过**家庭成员绑定**把两端连起来：老人只需打卡 + SOS，家属端获取完整数据与告警。**降低老人学习成本，同时满足家属的知情需求。**

## c.3 产品创新

**适老化 + 专业化的双界面**

| 老人端 | 家属端 / 后台 |
|---|---|
| 大字号、大按钮 | 数据看板、告警处理 |
| 少层级、少输入 | 多维度统计 |
| 语音优先 | 批量管理 |

同一套后端，两套信息架构。**后台管理端（Vue）独立部署**，服务社区/机构场景。

## c.4 技术创新

**三层 AI 降级的鲁棒性架构**

```
Ollama（本地、免费、快）→ Coze（云端、强、有成本）→ 规则库（永远可用）
```

- 解决了"云端 AI 不可靠导致的用户体验崩塌"
- 解决了"老年用户无法理解技术错误"的问题
- 成本可控：优先走免费本地模型

**另一个技术点**：原项目有 5 处密钥泄露（含前端硬编码 Token），本次重构将全部 AI 调用后移到后端，**前端零密钥**。这既是安全改进，也是架构正确性证明。

## c.5 商业模式创新

【待填，取决于小程序主体类型】

**若为个人主体**（无法开通支付）：

- 免费基础版 + 增值服务（付费问诊导流、健康师咨询）
- 与社区/养老机构合作，机构付费、老人免费
- 硬件联动（智能手环/跌倒检测器）分成

**若为企业主体**：

- B2C 订阅：家属端高级功能（多长辈管理、健康报告导出）
- B2B 服务：社区/养老机构批量部署，按人头收费
- 硬件 + 服务套餐

## c.6 用户体验创新

**适老化设计的系统性落地**

| 设计点 | 做法 |
|---|---|
| **大字号模式** | 原项目有 CSS 但未挂载，本次修复并加开关 |
| **长按 SOS** | 3 秒长按（原代码实际 1 秒，与文案不符，已修正） |
| **语音优先** | 支持语音输入，减少打字 |
| **TTS 播报** | 回复可语音朗读 |
| **错误友好** | 任何 AI 失败都降级，不显示技术错误 |
| **真实数据** | 原项目睡眠评分是硬编码假数据，本次改为真实计算 |

> 💡 **"修复了 14 处原项目缺陷"这件事本身可以作为创新点讲**——它体现工程严谨性。

示例（`AiService.java` 摘录）：

```java
/**
 * AI 编排服务 —— 三层降级
 * 路由顺序（任何一层失败都自动降级，绝不向用户报错）：
 *   ① Ollama（本地模型，最快最省钱）
 *   ② Coze（云端模型，能力强）
 *   ③ 规则库（本地兜底，永远可用）
 */
public String chat(String userId, String message) {
    if (aiEnabled) {
        String r = tryOllama(message);
        if (r != null) return r;
        r = tryCoze(message);
        if (r != null) return r;
    }
    return ruleProvider.reply(message, context);   // 兜底
}
```

## d.6 难点与解决方案

| # | 难点 | 解决方案 |
|---|---|---|
| 1 | **AI 服务不可靠** | 三层降级链，任一层失败自动切换，用户无感知 |
| 2 | **老年用户操作困难** | 大字号、长按 SOS、语音输入、TTS 播报 |

## g.2 用户增长设计

**冷启动：从"子女"切入**

老人不会主动下载，但子女会为父母寻找解决方案。

```
子女发现需求 → 下载并注册 → 生成邀请码 → 老人扫码绑定
                                            ↓
                                    老人零学习成本进入
```

**传播路径**：

1. **微信分享**（已接入）：家属邀请家人共同关注
2. **社区地推**：与养老服务中心合作，现场安装
3. **医院/药店**：慢性病患者场景导流
4. **口碑裂变**：老人用得好的家庭会推荐给同龄朋友

**目标**：前 6 个月 1,000 个家庭，12 个月 5,000 个家庭。

## g.3 运营机制

| 机制 | 设计 |
|---|---|
| **激活** | 绑定家属后推送"首次守护报告" |
| **留存** | 每日打卡提醒 + 每周健康报告 + 关怀推送 |
| **防流失** | 连续 3 天未打卡 → 提醒家属关注 |
| **活跃** | 打卡连续天数激励、健康分提升 |
| **服务闭环** | 告警 → 家属处理 → 处理结果记录 |

## g.4 商业闭环

【待填，按主体类型选择】

```
收入端                          成本端
├─ B2C 订阅（家属增值功能）       ├─ 服务器（云主机）
├─ B2B 服务（社区/机构）          ├─ AI API 费用
├─ 硬件分成                       ├─ 短信费用
└─ 健康服务导流分成               └─ 运营人力
```

**成本优化（已实现）**：

- **优先走 Ollama 本地模型**，零 API 成本
- Coze 仅作为第二层兜底，用量可控
- 规则库兜底保证极端情况下零成本运行

> 💡 **这个成本结构是加分点**：很多 AI 应用的成本模型不成立，
> 而三层降级天然实现了"低成本优先"。
